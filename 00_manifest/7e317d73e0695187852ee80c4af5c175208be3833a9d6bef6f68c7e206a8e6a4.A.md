# File Object Identity and Repository Seat Contract

이 계약은 AI 인스턴스가 Framework 자동번호, 설명형 파일명, Repository 이름변경 때문에 입력객체를 오독하지 않도록 고정한다.

## 1. File은 하나의 결정화 상태 Cell이다

```text
File
=
하나의 Exact Byte 상태
=
하나의 결정화된 상태 Cell
```

같은 의미처럼 보이는 문서라도 Exact Byte가 다르면 서로 다른 File Object다.

```text
Same Semantic Title
+ Different Exact Bytes
→ Different Objects
```

## 2. Hash Code File Name

불변 상태객체의 Canonical Filename:

```text
<64 lowercase SHA-256 of exact file bytes>.<Repository Seat Code>.<extension>
```

```text
Hash Code
→ Exact File Byte Identity

Repository Seat Code
→ Object가 등록되는 Repository 고정자리

Extension
→ 직렬화 형식
```

파일 본문 안에 자기 자신의 최종 Hash나 최종 Filename을 삽입하지 않는다.

```text
Temporary File
→ 계약된 Byte 동결
→ SHA-256 계산
→ Hash Filename 부여
→ 실제 Byte SHA-256 재계산
→ Filename 첫 Segment와 비교
```

## 3. Framework Transport Suffix

```text
file.md
file(1).md
file(2).md

<hash>.A.zip
<hash>.A(1).zip
<hash>.A(2).zip
```

```text
(숫자)
=
Framework Transport Suffix
≠ Version
≠ Revision
≠ History
≠ Original Marker
```

Input Identity:

```text
Normalized Canonical Filename
+
Exact File Bytes
+
Actual SHA-256
+
Repository Seat Code
+
Internal Object Metadata
=
Input Identity Binding
```

## 4. Same Bytes and Duplicate Copies

```text
Same Exact Bytes
+ Same Repository Seat Code
→ Same File Object
```

Framework가 `(1)` 또는 `(2)`를 붙여도 어느 복사본이 “진짜 원본”인지 구분하지 않는다.

```text
Same Exact Bytes
→ Same Object
```

```text
Different Exact Bytes
→ Different Hash Code
→ Different Object
```

```

A/B/C

```

## 6. Same Hash across Different Repository Seats

```text
<same-hash>.A.md
<same-hash>.B.md
<same-hash>.C.md
```

```text
Content Byte Identity
→ same

Repository-qualified Object Identity
→ different
```

```text
Hash Code
+
Repository Seat Code
=
Repository-qualified File Object Identity
```

## 7. Collision Gate

같은 Repository Seat에서 Filename Hash는 같지만 실제 Bytes가 다르면 자동 선택하지 않는다.

```text
HOLD_HASH_COLLISION_WITHIN_SAME_REPOSITORY_SEAT
```

검사:

```text
Exact Byte 비교
File Size
Secondary Digest
Object Metadata
Source Lineage
Repository Path
Commit·Tree·Blob
```

## 8. Semantic Control Surface와 Hash Object

Stable Entry는 고정경로를 위해 Semantic Filename을 유지할 수 있다.

```text
README.md
REPO_IDENTITY.md
CURRENT_STATUS.yaml
INSTANCE_GENERATION_INDEX.md
gpt.xyzt.md
HEAD_INDEX.json
```

불변 상태객체는 Hash Filename을 사용한다.

```text
Result
Result.Data
Track DB
Hash DB
History Event
Directive Payload
Closure Evidence
Publication Package
Execution Package
Head Object
```

Semantic Control Surface를 전달할 때는 Hash-named Deployment Package가 Exact Target Path를 지정한다.

## 9. Sidecar Boundary

Hash Filename Object는 Filename 자체가 Expected Hash를 가진다.

```text
Expected Hash
→ Filename first segment

Actual Hash
→ Exact Bytes
```

일반 Hash-named Object에는 외부 `.sha256.txt` 또는 `SHA256SUMS.txt` Pair를 기본 생성하지 않는다.
Sidecar는 실행기 또는 외부 표준이 명시적으로 요구할 때만 사용한다.
